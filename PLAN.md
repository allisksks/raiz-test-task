**Срок:** 21.10.2026 (ср) → **30.10.2026 (пт)** — 10 календарных дней.
**Code freeze:** 29.10 вечер. 30.10 — буфер, демо и сдача.

Сквозной сценарий, который должен работать к сдаче:

## 2. Архитектура

```
 ┌──────────┐   OData / выгрузка XML/CSV   ┌────────────────────────────┐
 │   1С     │ ───────────────────────────▶ │                            │
 └──────────┘                              │   ETL (Python)             │
 ┌──────────────────────┐   SQL/CSV/XLSX   │   - extract → staging      │
 │ Подготовленная база  │ ───────────────▶ │   - нормализация, матчинг  │
 │ (цены, конкуренты)   │                  │   - история (SCD2)         │
 └──────────────────────┘                  └─────────────┬──────────────┘
                                                         ▼
                                           ┌────────────────────────────┐
                                           │ PostgreSQL                 │
                                           │  staging → core → marts    │
                                           │  + signals, hypotheses     │
                                           └─────────────┬──────────────┘
                                ┌────────────────────────┼───────────────┐
                                ▼                        ▼               ▼
                     Детектор сигналов          Движок гипотез     BI (карта РФ,
                     (по расписанию)            (правила + веса)   drill-down)
```

**Стек:** Python 3.12 (ETL, сигналы, гипотезы), PostgreSQL 16, BI, Docker Compose (поднимается одной командой), pytest, GitHub Actions (lint + tests).

**BI — решение на день 1** (рекомендация — Apache Superset):
- **Apache Superset** (рекомендуется): self-hosted в Docker, есть карта России по регионам (Country Map), cross-filters, drill-down; проверяющий запускает всё через `docker compose up`.
- Yandex DataLens: удобная карта РФ из коробки, но облачный сервис, его сложнее приложить к репозиторию.
- Power BI / Visiology: если этого требует заказчик; витрины в Postgres подойдут для любого из них.

Всё, что BI показывает, считается в **витринах Postgres**, так что BI-инструмент можно заменить без переделки логики.

## 3. Модель данных (core)

| Сущность | Ключевые поля |
|---|---|
| `region` | код ОКАТО/ISO 3166-2:RU, название, ФО |
| `channel` | опт / дистрибуция / розница / … |
| `company` | id, тип (`client` / `competitor`), ИНН, канал, `first_seen_at` |
| `company_region` | компания × регион, период присутствия |
| `product_group`, `product` | номенклатура, группа, ед. изм., признак «аналог/заменитель» |
| `product_match` | связь товара конкурента с товаром клиента: `identical` / `similar` |
| `price_observation` | регион × компания × товар × канал × дата, цена, **источник**, **достоверность** |
| `sales_fact` (из 1С) | клиент × регион × товар × период: объём, выручка, себестоимость, маржа |
| `margin_plan` (из 1С) | план маржи по тем же разрезам |
| `market_share` | регион × группа × участник × период, доля, `is_estimated` |
| `signal` | тип, разрезы, значение, порог, severity, статус |
| `hypothesis` | signal_id, тип причины, score, обоснование, **`kind = fact / estimate / hypothesis`** |
| `data_source` | реестр источников (см. §6) |

Признак происхождения каждого числа (`fact` / `estimate` / `hypothesis`) хранится в данных и выводится в BI отдельным цветом или меткой, как требует ТЗ.

## 4. Интеграции

### 4.1. 1С
- **Основной путь:** стандартный REST-интерфейс OData 1С (`/odata/standard.odata/`): справочники «Контрагенты», «Номенклатура», регистры продаж/себестоимости, план маржи.
- **Запасной путь** (если нет доступа к живой базе): регламентная выгрузка XML/CSV (CommerceML или своя обработка) в папку или S3, ETL забирает файлы.
- Для разработки: **мок 1С** — фикстуры в формате ответа OData, чтобы ETL и тесты не зависели от доступа.
- Инкремент по дате изменения, идемпотентная загрузка (upsert по GUID 1С).

### 4.2. Парсинг с подготовленной базы
- Источник: подготовленная база цен и конкурентов (SQL-дамп / CSV / XLSX — формат зафиксировать в день 1).
- Загрузчик: схема-валидация (pydantic), нормализация регионов (справочник синонимов → код региона), нормализация названий и ИНН конкурентов, матчинг номенклатуры (артикул → нечёткое совпадение по названию + ручной словарь).
- Каждая запись получает `source_id` и `reliability` и попадает в историю: изменения не перезаписываются, а добавляются как новые наблюдения.
- Интерфейс `Source` сделан так, чтобы после MVP подключить живые парсеры (сайты, маркетплейсы, тендеры) без изменения ядра.
- При нехватке данных — **генератор синтетических данных** с пометкой `estimate`, чтобы показать сценарии сигналов.

### 4.3. BI
- Подключение к схеме `marts` в Postgres (read-only пользователь).
- Дашборды:
  1. **Карта РФ**: клиенты и конкуренты по регионам, индекс цены клиента к рынку, число новых конкурентов.
  2. **Регион**: участники по каналам, доли и их динамика, цены по номенклатуре.
  3. **Клиент → номенклатура**: план/факт маржи, ценовая позиция против конкурентов.
  4. **Лента сигналов**: событие, шаблонный текст, переход к гипотезам.
  5. **Гипотезы / ценовая архитектура конкурента**: разложение цены и вес каждой гипотезы.
  6. **Источники данных**: реестр, свежесть, достоверность.
- Фильтры (§9 ТЗ): регион, клиент, конкурент, продукт, канал, диапазон цены, «только новые конкуренты», период, динамика.
- Экспорт дашбордов в репозиторий (`bi/`), чтобы они восстанавливались при развёртывании.

## 5. Логика сигналов и гипотез

**Сигналы** (запуск после каждой загрузки, пороги в конфиге):

| Сигнал | Правило (по умолчанию) |
|---|---|
| Новый конкурент | `first_seen_at` в регионе клиента за период |
| Изменение цены конкурента | \|Δ\| ≥ 5% к предыдущему наблюдению |
| Отклонение от цены клиента | цена конкурента ниже/выше цены клиента на ≥ 10% |
| Изменение ценовой позиции клиента | сдвиг индекса цены клиента к медиане рынка ≥ 5 п.п. |
| Новый товар-заменитель / изменение ассортимента | новые/исчезнувшие `product` у конкурента |
| План ≠ факт по марже | отклонение ≥ 3 п.п. |
| Изменение доли рынка | Δ доли ≥ 2 п.п. |
| **Составной сигнал** | маржа ↓ **и** новый конкурент с ценой ниже — текст: «В регионе появились новые конкуренты с ценой на x% ниже цены клиента. Одновременно маржа клиента снизилась на x%.» |

**Гипотезы** («за счёт чего конкурент дешевле»): набор правил, каждое даёт score 0–1 и текстовое обоснование на основе доступных фактов:
- прямые закупки у производителя / меньше посредников — канал конкурента и цена близка к оценке закупочной;
- региональный склад / логистика — цена ниже только в регионах рядом со складом;
- агрессивный выход — новый конкурент + цена ниже рынка + короткая история;
- временное снижение маржи — краткосрочная акция, цена возвращается;
- объёмы закупок / другая структура затрат — широкий ассортимент, крупный канал (опт).

**Ценовая архитектура:** разложение цены конкурента на закупку → логистику → наценку канала → маржу, с пометкой, какие компоненты являются фактом, а какие оценкой.

**Доли рынка:** факт, если есть объёмы; иначе оценка по статистике прошлых периодов (тренд или скользящее среднее) с пометкой `estimate`.

## 9. Риски

| Риск | Митигирующие меры |
|---|---|
| Нет доступа к живой 1С | Мок OData + файловая выгрузка; подключение в конце |

| Ограничения BI на drill-down по карте | Расчёты в витринах; на крайний случай — простая веб-страница с картой поверх витрин |
