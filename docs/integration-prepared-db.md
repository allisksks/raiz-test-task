# Интеграция с подготовленной базой конкурентов

Подготовленная база — результат парсинга открытых источников: сайтов и прайс-листов конкурентов, маркетплейсов, полевого мониторинга. Загрузчик читает её через SQLAlchemy, поэтому база может быть:
- SQLite-файлом — так устроены тестовые данные в `data/samples/prepared/prepared.sqlite`;
- PostgreSQL, MySQL или MS SQL — с той же структурой таблиц.

Структура таблиц (`sources`, `competitors`, `competitor_regions`, `offers`, `prices`) описана в [test-data.md](test-data.md#формат-подготовленной-базы-sqlite). Если реальная база устроена иначе, проще всего сделать в ней представления (views) с этими именами и полями.

## Запуск

```bash
market-map load-1c          # сначала своя номенклатура — с ней сопоставляются товары конкурентов
market-map load-prepared    # адрес базы — PREPARED_DB_URL (по умолчанию тестовый SQLite)

market-map load-prepared --path /mnt/exchange/prepared.sqlite
PREPARED_DB_URL=postgresql+psycopg://user:pass@host/parsing market-map load-prepared
```

В Docker: `docker compose run --rm app load-prepared`.

## Что происходит при загрузке

| Шаг | Куда | Обработка |
|---|---|---|
| Источники наблюдений | `core.data_source` (`prepared_db:<id>`) | Тип и достоверность (A/B/C) сохраняются: по ним потом видно, насколько можно доверять цене |
| Конкуренты | `core.company` (kind = competitor) | Канал из свободного текста приводится к справочнику («опт», «Оптовая торговля» → опт). Дата регистрации, региональный склад и схема поставок сохраняются для гипотез |
| Присутствие в регионах | `core.company_region` | Регион распознаётся по вариантам написания. `last_seen` → `valid_to`: конкурент ушёл из региона |
| Предложения | `core.product` (с `company_id` конкурента) | Если артикула нет в поле, он ищется в названии: «… (арт. PM-101)», «PM-101 …». Из названия артикул убирается |
| Сопоставление | `core.product_match` | См. ниже |
| Цены | `core.price_observation` | Текст разбирается в число («1 234,50 ₽» → 1234.5). Канал наблюдения — канал конкурента. Происхождение — `fact` |

Повторная загрузка тех же данных ничего не дублирует. Изменения в `core` пишутся одной транзакцией. Нераспознанные записи (регион, цена, категория) попадают в `staging.load_reject` с причиной и не останавливают загрузку. Журнал запусков ведётся в `staging.load_run`.

## Сопоставление с номенклатурой

1. **Артикул совпадает** со своим (в поле или в названии) → идентичный товар, уверенность 1.0.
2. **Иначе сравниваются названия** в пределах той же группы товаров. Перед сравнением из названий убираются бренды и артикулы, регистр и запись единиц («30кг» / «30 кг») приводятся к одному виду. При сходстве от 0,85:
   - бренд тот же → **идентичный** товар;
   - бренд другой → **схожий** (аналог).
3. Не нашлось пары → товар остаётся без сопоставления (`unmatched` в статистике). Его цены хранятся, но в сравнении с ценой клиента не участвуют.

Если автоматика ошиблась, сопоставление правят вручную в `core.product_match` с `method = 'manual'`. Ручные сопоставления при повторной загрузке не перезаписываются.

На тестовых данных все 234 предложения сопоставляются правильно (проверяется тестом против генератора). На реальных данных стоит посмотреть `unmatched` и выборочно проверить пары с уверенностью ниже 0,95.
